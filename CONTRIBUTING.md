# Contributing

If you have a feature idea or find a bug, please open an [issue](https://github.com/tldraw/obsidian-plugin/issues). The rest of this file describes how the plugin is built, tested and released.

## Setup

Use the Node version in [`.nvmrc`](./.nvmrc), then run `npm i`.

## Building

- `npm run dev` builds into `dist/development/`.
- `npm run build` builds into `dist/production/`.
- `npm run vite:dev` is the Vite alternative to `npm run dev`, with fast HMR. `npm run vite:build` is the Vite alternative to `npm run build`.

Each output folder holds `main.js`, `styles.css` and `manifest.json`. Copy or link that folder into a vault as `.obsidian/plugins/tldraw`, then disable and re-enable the plugin in `Settings` > `Community plugins` to reload it.

Edit `src/styles.css`, not the `styles.css` at the root of the repo.

## Project layout

- `src/` is the plugin source.
- `dist/` is the compiled output (generated by the build).
- `release/` holds the files used for a release: `manifest.json` and `versions.json`.
- `test/` holds the unit tests (`test/unit/`), the end-to-end specs (`test/specs/`) and the fixture vaults (`test/vaults/`).

`src/` is split into layers, and the `boundaries` rules in `eslint.config.mjs` enforce what each layer may import:

| Layer | Folders | May import |
| --- | --- | --- |
| `obsidian` | `src/obsidian` | `obsidian`, shared |
| `tldraw` | `src/tldraw` | `tldraw` packages, shared |
| `plugin` | `src/plugin` | everything. It is the only layer that connects `obsidian` and `tldraw`. |
| shared | `src/utils`, `src/lib`, `src/types`, `src/assets` | shared only |

Only the `obsidian` and `plugin` layers may import the `obsidian` package, and only the `tldraw` and `plugin` layers may import `tldraw` packages. The entry point, `src/main.ts`, imports only from `plugin`.

## Checks

These run in CI (`.github/workflows/checks.yml`) on pushes to `main` and on pull requests:

- `npm run lint` runs ESLint, including the layer rules.
- `npm run lint:obsidian` runs the [Obsidian plugin review rules](https://github.com/obsidianmd/eslint-plugin) from their own config, `eslint.obsidianmd.config.mjs`.
- `npm run typecheck` type-checks the source, the scripts and the end-to-end specs. The unit tests are not type-checked.
- `npm run test:unit` runs the unit tests.

`npm run format-current` runs Prettier on the files you have changed. It re-sorts imports, so review the diff before committing.

## Unit tests

Unit tests live in `test/unit/` and run with [Vitest](https://vitest.dev/) in a jsdom environment. They don't run Obsidian: `obsidian` is replaced by the stub in `test/unit/helpers/obsidian-stub.ts`, so add to the stub when a test needs more of the API.

## End-to-end tests

End-to-end tests run [WebdriverIO](https://webdriver.io/) against a real Obsidian instance using [`wdio-obsidian-service`](https://github.com/jesse-r-s-hines/wdio-obsidian-service). Specs are the `*.e2e.ts` files in `test/specs/`, and the default vault is `test/vaults/default`. The runner needs a plugin to load: by default it uses the production build in `dist/production/`, so build first.

```bash
npm run build
npm run e2e
```

On Linux the tests need a display, so CI runs them under `xvfb-run`.

To use a different plugin build, set one of these:

- `TLDRAW_PLUGIN_DIR` is the path to a plugin folder (the directory that contains `manifest.json`, `main.js` and so on).
- `TLDRAW_PLUGIN_VERSION` installs the published plugin with id `tldraw` at this version from the community registry, instead of using a local folder.

Configuration is in `wdio.conf.mts`. Timeouts, the Obsidian installer version and other options are documented in the [sample plugin config](https://github.com/jesse-r-s-hines/wdio-obsidian-service-sample-plugin/blob/main/wdio.conf.mts).

## Releasing

A release is made in two steps:

1. Open a pull request that bumps the version. Set the new version in `package.json` (and `package-lock.json`), then run `npm run version`. That copies the version into `release/manifest.json` and adds it to `release/versions.json` with the plugin's `minAppVersion`.
2. After it is merged, run the **Manual Release** workflow in GitHub Actions on `main`. It tags the version from `package.json`, builds the release files and attests them, publishes the release, and commits the updated `manifest.json` and `versions.json` back to `main`.

See [Creating a Release](./release/README.md) for what the packaging scripts do.

To check a published release, run the **Verify Release** workflow from the Actions tab, or `gh workflow run verify-release.yml -f tag=<version>`. It rebuilds the tag from a clean checkout and checks that the release's `main.js`, `styles.css` and `manifest.json` are identical and carry a build attestation.
